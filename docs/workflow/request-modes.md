# 按请求范围进入流程

在启动 production 前先区分用户要完成什么。此分流不改变现有 job 的质量标准，不新增 review_mode。

| 请求 | 应执行 | 完成条件 |
|---|---|---|
| 只读检查/诊断现有模型 | 读取指定模型与来源；网页观察或隔离副本审计；输出缺陷、未知与可行路线 | 检查报告覆盖本次问题；明确未测项，不写最终 accepted |
| 下载/恢复同版已有结果 | workflow status；核对 run、URL/版本与实际任务；使用原导出/Bridge 回执恢复；校验文件 | 请求的文件可用且来源/依赖/哈希已记录，不因此通过制作质量链 |
| 完整制作或正式交付 | scaffold（新资产）→配置 production→所需远程/本地操作→质量关卡 | 当前请求的交付、技术证据及真实最终验收完成 |

只读检查不强制新建 production，不因没有动作意图要求补动作。无新增制作预算仍可收集已有文件的证据。下载恢复无 production 时可用 `node tools/workflow/workflow.mjs status ASSET`；GLB 基础检查可用 `node tools/workflow/workflow.mjs inspect-glb FILE`。基础 GLB 检查不是完整拓扑/视觉验收。

已有 production 时先 next，任何未决执行/传输优先对账。轻量请求不得绕过未决操作或改变其源，不能假称完成整个 job。只有新的真实制作需求才配置完整 job。静态正式交付仍按适用的 base_model、polish、final 验证；不要求不存在的 rig/motion/engine。

## 初次归档外部文件

现有 worker 和固定采图器以已保存 `.blend` 为输入。GLB/FBX 等先独立接收/导入，归档是传输准备，不冒充 geometry_repair 的质量改善。

1. 核对实际源文件、格式、依赖哈希和用户范围；保存原件。
2. 独立后台进程或已确认干净的接收场景导入，输出新的 `.blend`，不替换未保存 live 场景。
3. 保存导入脚本/命令、Blender 实际版本、输入哈希、对象/材质/骨架/片段清单、依赖缺失项与输出哈希。导入只做必要格式转换；修改几何/材质需要后续制作计划。
4. transfer received 回执的 candidate 指向归档 `.blend`；source_identity 与证据指向原始文件/Studio 版本；attach-source 引用同一回执。仅本地源也保留同样来源链，无需虚构远程 run。
5. 导入失败或结果未知先核对当前文件和进程，不能覆盖预留输出重试。成功归档只允许开始验证，不自动通过 base_model。

## Blender返回Studio的交换副本

需要使用Studio原生绑定/动作或其他兼容处理时，从已保存、结构稳定的母版另存交换副本；母版及已验收动作保留。纯GLB/FBX序列化属于传输准备，不是正式`export`批次，不产生`export_verified`。记录母版与交换文件哈希、实际导出设置、对象/材质/骨架/clip清单，核实当前上传入口、格式及报价，并将副本身份绑定到本次输入。

交换准备不能顺便改几何、UV、权重或外观；实际内容修改仍按正常制作计划和原预算执行。返回结果另存、按独立来源接收，先核查实际属性和完整动画再选择候选；页面“已绑定”和clip名称不证明输入骨架/旧动作保留。详见 [往返规范](roundtrip.md)。

正式静态制作的最小技术范围是：设计/结构和可制作性、外观与适用几何/材质、可编辑母版、所需输出及干净回读。数值测量只对适用指标要求；默认视觉证据使用归档 Blender 的冻结采图。只下载不应被强制升级到该完整范围。
