# Tripo 网页积分默认自主使用

> 开源使用说明：以下持续授权属于原作者账户，不适用于克隆仓库的其他操作者。新操作者须将资产 policy 中的 credit_authorization.evidence 替换为自己的真实授权；如需显式预算，设 mode=explicit_budget 并填写上限。任务尚未获得授权时不得提交。

2026-10-14 用户明确要求：“不要针对tripo额度的问题，默认要设置不询问用户，自己消耗即可，反复询问很影响进度”。这是本工作流持续有效的费用授权，适用于当前及后续资产任务。

- 在用户任务范围内，自主使用当前账户已有 Studio 网页积分，不询问每次费用，不要求用户设积分预算或付费次数，不因旧积分上限重复请批。生成、必要重试和后处理均适用。
- 每次仍读取实际报价、当前可用余额、目标输入和版本；余额足够直接执行并记录。余额不足时报告无法继续，不自动充值、购买套餐或切换 API。维护工作本身不要求为了测试而生成无关资产。
- scope、参考、技术质量和审阅规则继续适用；费用授权不改变用户设计要求。任务所需操作从已明确请求配置，不把填写 policy 变成费用审批。参考/节奏/最终审阅不属于费用询问。
- 未知提交和进行中任务先对账，不重复扣费。失败原因未改变不盲目重试；同一策略连续两次无改善先诊断换路。达到目标即停止，不把无积分上限解释为无限循环。
- 本地 Blender 返工上限与质量停止规则未被本次 Tripo 费用偏好修改。

## 执行配置

新 scaffold 自动写入 `credit_authorization.mode=autonomous_existing_balance`，evidence 指向本次真实用户指令。现有资产 policy 同步此字段，原 studio_credit_cap/max_paid_runs 留作历史，但此模式不再用它们阻止新提交。未改动旧 run、已花积分、验收、参考或模型。

prepare 自动生成绑定当前计划哈希和当前报价的 approval，`authorization_kind=standing_user_instruction`，不是伪造新的人类逐次批准。已有 planned run 在 check-plan 时使用此持续授权，mark submitting 通过全部检查后保存到该 run。已提交、失败和未知 run 不重写授权。仍执行单候选、页面实值、来源、范围与质量检查。

消耗继续记账，缺失历史费用显示 unknown/null，不臆造零费用或退款。此模式不依靠无法确定的历史累计消费阻止使用当前可用余额。

仅当用户之后明确要求恢复逐次审批或设定新费用上限时，才切回显式预算模式（移除该字段或设 mode=explicit_budget 并配置真实上限）。旧资产的历史数字本身不是新的用户限制。
